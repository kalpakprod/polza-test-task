# ANOMALIES.md — что не так с `data/review.csv`

Всего строк в файле: **207** (без заголовка). Из них **107** чистых, **100** с хотя бы одной проблемой.

Как искал: файл грузится в `review_raw` **как есть** (все колонки `text`), рядом пишутся
очищенные значения и массив `issues[]`. Ни одна строка не выбрасывается — иначе аномалию
нельзя доказать. Отчёт получается одним запросом:

```sql
SELECT unnest(issues) AS issue, count(*) FROM review_raw GROUP BY 1 ORDER BY 2 DESC;
```

---

## 1. Главная аномалия: это выгрузка НЕ той же базы

`review.csv` подан как «свежая выгрузка для той же базы». Фактически из 207 строк с базой
компаний совпадают только **6 id**.

```sql
SELECT count(*) FROM review_raw r JOIN company c ON c.id = r.ext_id;  -- 6
SELECT min(ext_id), max(ext_id) FROM review_raw;  -- c_000098 .. c_900011
SELECT min(id), max(id) FROM company;             -- c_000001 .. c_001000
```

- В `page_*.json` диапазон id — `c_000001 … c_001000`.
- В CSV основная масса — `c_001004 … c_001190`, то есть **за пределами выгрузки**.
- Плюс 6 строк с id вида `c_900006 … c_900011` — вообще другая нумерация (флаг
  `id_out_of_source_range`).

Как обнаружил: сравнил `min/max` id и сделал `JOIN` по `ext_id`. Совпало 6 строк — и у этих
шести **все поля идентичны** JSON-выгрузке (`name`, `city`, `rating`, `reviews_count`),
то есть это не «обновление данных», а случайное пересечение.

Вывод: файл нельзя грузить в `company` как обновление. Либо перепутали выгрузку, либо это
следующая страница другого прогона парсера. Пока лежит отдельной таблицей `review_raw`.

## 2. Название файла не соответствует содержимому

Файл называется `review.csv` и должен, судя по имени, содержать отзывы. Внутри — те же
9 колонок, что и у компаний: `id,name,category,city,address,rating,reviews_count,site,phone`.
Ни текста отзыва, ни автора, ни даты. Это не отзывы, а справочник компаний.

## 3. Два полностью пустых хвоста

Строки 207 и 208 файла — пустые (`,,,,,,,,`). Флаги: `id_empty`, `name_empty`,
`category_empty`, `city_empty`, `reviews_empty`, `address_empty`.
Обнаружил через `count(*) FILTER (WHERE ...)` по пустым значениям каждой колонки.

## 4. Дубли id (3 строки)

```sql
SELECT ext_id, count(*), array_agg(row_number)
FROM review_raw WHERE ext_id IS NOT NULL GROUP BY 1 HAVING count(*) > 1;
```

| id | строки |
|---|---|
| `c_001075` | 7, 206 |
| `c_001049` | 42, 204 |
| `c_001050` | 117, 205 |

Все три дубля сидят в самом конце файла (204–206) — похоже на дописанный руками хвост.

## 5. Рейтинг: четыре разных дефекта

| Проблема | Кол-во | Пример |
|---|---|---|
| `rating_empty` | 20 | пустая строка |
| `rating_not_a_number` | 1 | `c_001083` → `N/A` |
| `rating_comma_decimal` | 1 | `c_001010` → `4,5` (запятая вместо точки) |
| `rating_out_of_range` | 2 | `c_001122` → `-3`, `c_001186` → `7.5` |

Рейтинг вне `0..5` — уже не «грязь формата», а невозможное значение: в схеме на это стоит
`CHECK (rating BETWEEN 0 AND 5)`, поэтому такие значения не попадают в `rating_clean`.

## 7. Город: сдвиг колонок, мохибейк, регистр, пробелы

- **Сдвиг колонок**: `c_001015` — в `city` лежит адрес `ул. Советская, д. 89, офис 43`
  (`city_looks_like_address`). Нашёл регуляркой на `ул.|д. \d|офис` внутри поля города.
- **Мохибейк** (`city_mojibake`, 2 строки): `c_001008` → `РњРѕСЃРєРІР°`, `c_001128` →
  `РЎР°РЅРєС‚-РџРµС‚РµСЂР±СѓСЂРі`. Это UTF-8 байты кириллицы, прочитанные как cp1251.
  Восстанавливаются как `value.encode('cp1251').decode('utf-8')` → `Москва`,
  `Санкт-Петербург`. Значит, часть файла прошла через ещё одну перекодировку.
- **Регистр и латиница** (`city_normalized`, 3 строки): `москва`, `Moscow`,
  `Санкат-Петербург` (опечатка).
- **Хвостовой пробел** (`city_trimmed`, 1): `Москва `.

Итого один и тот же город приходит минимум в 6 написаниях — без нормализации любой
`GROUP BY city` даст мусор.

## Что нашёл в основной выгрузке `page_*.json` (для полноты)

- Прочитано 1000 строк из 20 файлов, при `total: 1000` в метаданных — совпадает.
- **6 дублей по `id`** (`c_000285` и др.), payload у дублей **побайтово идентичный** —
  то есть это повтор строки при пагинации, а не конфликт данных. Все 1000 физических
  строк лежат в `company_source`, дубли помечены `is_duplicate = true`; в `company`
  уникальных — **994**.
- Пропуски по канонической части: `site` — 238, `phone` — 110, `rating` — 79. Это NULL
  в исходнике, а не битые значения.

## Как это влияет на запросы

- Средний рейтинг считаю через `avg(rating)` и отдельно вывожу `count(rating)` — иначе
  79 NULL молча искажают картину «по количеству компаний».
- Долю с сайтом считаю как `count(site) / count(*)`: 238 NULL — это «нет сайта», а не
  «нет данных о сайте», иначе процент завышается.
